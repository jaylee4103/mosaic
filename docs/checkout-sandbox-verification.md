## Next.js board checkout verification

On September 26, 2026 (US Eastern time), the Next Route Handlers were exercised against the configured Supabase project and two distinct Stripe test merchant accounts. A guest board cart contained a $34.00 Terracotta Planter from Sol & Clay and a $26.00 Linen Table Runner from North Loom. `POST /api/boards/:boardId/checkout` saved one $60.00 checkout with two merchant orders; calling it again returned the same checkout. Cart mutation was rejected after checkout started.

After restarting Next, `GET /api/boards/:boardId/checkout` loaded the same session from Supabase. `POST /checkout/payments` created one `cs_test_` hosted Checkout Session per merchant. The $34.00 merchant payment completed first; `GET /checkout/payments` reported `partial`, with Sol & Clay paid via Link and North Loom unpaid. Calling `POST /checkout/payments` again skipped Sol & Clay and resumed North Loom's existing unpaid session. After the $26.00 payment, both merchant orders reported `paid`, `paymentMethodType: "link"`, and `linkVerified: true`; the checkout reported `completed`. A further payment request created no new sessions, and `GET /cart` returned a fresh empty cart.

The test created checkout through a script with its own guest cookie. Stripe's return page opened in a different browser session and therefore showed `404 Board not found`; calling the same return route with the original guest cookie returned `completed`. The local API test used `bun dev` so the guest cookie could be sent over HTTP localhost; `next start` sets a Secure cookie and needs HTTPS for a real browser checkout. The frontend does not yet start checkout, so a full browser-only round trip remains to be tested when its checkout UI is added. No real funds moved, and no physical merchant orders were placed. The local and production limits are in [`../apps/web/README.md`](../apps/web/README.md).
